# 祭祀碑牌按词条显示手工价签：文件分析结果

分析日期：2026-09-20。目标：`D:\poe2` 当前安装。

## 结论

按照用户追加条件，目标是：**祭祀碑牌 + 怪物效用词条 → 显示手工价签 1D**，不区分词条的具体数值。

现有名称替换功能不能直接完成这一条件判断。只修改祭祀碑牌的基础名称，可以让所有祭祀碑牌显示 `祭祀碑牌=1D`，但没有效用词条的祭祀碑牌也会显示。修改“神話”“絕境”名称词库，也不能可靠识别效用词条，并且会影响其他使用相同名称词的物品。

找到了有静态依据的纯资源方案：让祭祀碑牌独立使用词缀描述规则，在其怪物效用词条后显示 `=1D`。该方案需要验证客户端是否接受独立模板和新增资源路径，目前不能宣称已经可用。它修改的是提示框内的词条文本，不能据此宣称能动态修改顶部黄色名称。

如果一定要求准确识别“类型 + 词条”，又不读取内存，读取游戏复制出的物品文本并在外部显示价签是更直接的实现路线；但这需要外部工具，效果不是修改游戏原生名称。

## 范围与方法

授权、范围和最新条件见 [scope.md](analysis/2026-09-20-ritual-tablet/scope.md)。

- 使用当前项目自带的 `LibGGPK3 / LibBundle3 / LibBundledGGPK3` 读取 GGPK。
- 所有实际打开游戏归档的分析命令均使用 `FileMode.Open + FileAccess.Read + FileShare.ReadWrite`。提取副本写入系统临时目录。
- 检查了 4,262,817 条虚拟文件索引；提取并检查相关 DAT、27 份顶层词缀描述文件、277 份物品 `.it` 模板。
- DAT 通过固定行、字符串指针、关联表和跨语言数据交叉核实。公开 schema 仅作参考；其部分尾部字段与本地版本不能完整对齐，因此没有把整张表按最新 schema 强行解码。
- 未修改游戏文件、项目功能代码，未读取进程内存。新增文件仅为本报告、范围说明和证据摘要。
- 本次分析对象是资源数据。PE 导入表、IAT、函数反编译和运行时 Hook 不适用，也未声称执行过这些步骤。

归档分析前后大小均为 `151463952901` 字节，最后写入时间均为 `2026-09-19 22:59:34.0611709 +08:00`。这是文件元数据核对，不冒充对整个约 151 GB 归档做过完整哈希验证。

## 已核实的资源关系

下文行号均为 DAT 的 **0 基行索引**，不是文本编辑器行号。

### 1. 祭祀碑牌可以按底材单独定位

`data/balance/traditional chinese/baseitemtypes.datc64`：

| 字段 | 本地实际值 |
|---|---|
| 行索引 | 4399 |
| Id | `Metadata/Items/TowerAugment/RitualAugment` |
| Name | `祭祀碑牌` |
| ItemClass | 107 |
| Tags | `tower_augment_ritual`, `tower_augment` |
| InheritsFrom | `Metadata/Items/TowerAugments/TowerAugment` |
| Implicit_Mods | 5084 |

其他七类碑牌各有独立基础表行，但都引用同一个 `InheritsFrom`。因此只改基础表第 4399 行的名称可以限定底材，却不能区分该底材内部的不同词缀实例。

当前项目 `poe2_name_price_patch.py` 的 `scan_base_item_names` 正是按基础表行读取名称；它并没有每一件碑牌的实际随机词缀数据。

### 2. 怪物效用不是祭祀碑牌专属词条

`data/balance/mods.datc64` 第 5097 行：

| 字段 | 本地实际值 |
|---|---|
| Id | `TowerMonsterEffectiveness1` |
| 词缀名 | `Challenger's` / `挑戰者的` |
| Domain | 34，与各类碑牌基础行相同 |
| GenerationType | 1，前缀 |
| Stat1 | `map_monster_potency_+%`，Stats 第 24372 行 |
| 数值范围 | 10～15 |
| 生成标签 | `default`，不是仅限 `tower_augment_ritual` |

作为对照，祭祀重骰费用词条 `TowerRitualRerollCostIncrease` 使用 `tower_augment_ritual` 与 `default` 标签，权重分别为 1 和 0。

因此直接修改共用效用词条的名称或描述，不能保证其他类型碑牌不受影响。把数值条件放宽为“存在词条”并不会自动解决类型隔离问题。

### 3. 黄色随机名称不等于词缀名称

`data/balance/traditional chinese/words.datc64`：

| 行 | 原词 | 显示词 | 有非零权重的标签 |
|---|---|---|---|
| 26 | `Mythic` | `神話` | `tower_augment`, `primordial_map` |
| 1857 | ` Apex` | ` 絕境` | `tower_augment` |
| 2283 | `Mythical` | `神話` | `tower_augment`, `expedition_logbook` |

这些条目属于名称词库，标签并非只针对祭祀碑牌，也没有指向 `TowerMonsterEffectiveness1` 的条件关系。截图中的名称不能当成“带效用词条”的唯一标识。

### 4. 词缀文本有单独的资源入口

`metadata/items/toweraugments/toweraugment.it` 中存在：

```text
Mods
{
    stat_description_list = "Data/StatDescriptions/tablet_stat_descriptions.csd"
    enable_rarity = "normal"
    enable_rarity = "magic"
    enable_rarity = "rare"
    enable_rarity = "unique"
}
```

当前 `.it` 与 `.csd` 都是可解码的文本资源。原始资源使用 UTF-16；本报告及证据 JSON 使用 UTF-8。未来若制作补丁，不能不经验证就把游戏原资源改存成 UTF-8。

`data/statdescriptions/tablet_stat_descriptions.csd` 的目标描述块包含：

```text
description
    1 map_monster_potency_+%
    2
        1|# "Monsters have {0}% increased [MonsterEffectiveness|Effectiveness]"
        #|-1 "Monsters have {0}% increased [MonsterEffectiveness|Effectiveness]" negate 1
    lang "Traditional Chinese"
    2
        1|# "增加{0}%怪物的[MonsterEffectiveness|效用]"
        #|-1 "增加{0}%怪物的[MonsterEffectiveness|效用]" negate 1
```

正值条件 `1|#` 已覆盖当前 10～15 的词条范围。如果能先隔离到祭祀碑牌专用描述文件，只需为这一显示分支附加 `=1D`，即可表达用户放宽后的条件，不必增加 12% 精确分档。

### 5. 祭祀类型标志存在，但跨组组合尚未验证

祭祀碑牌基础表关联的固有词缀为 `TowerAddRitualToMapsImplicit`，对应 `tower_add_ritual_to_X_maps`；该属性输出“在地圖內加入祭祀神壇 / 剩餘…次使用”。

描述语言也存在多属性组合：`map_stat_descriptions.csd` 将两个 tempest 名称属性合并输出；通用描述文件内找到 279 个多属性描述块。

但是，**支持多个属性的描述语法，不等于一次描述调用一定同时收到固有属性和显式词缀**。不能仅凭上述事实保证把 `tower_add_ritual_to_X_maps` 与 `map_monster_potency_+%` 放在同一描述块就能生效。

另外，`map_tower_augments_num_ritual_augments` 出现在 `EndgameMapTablets` 的地图效果映射中，不能直接当作物品词缀渲染时必然可见的条件。

## 可选方案与边界

| 方案 | 能满足的效果 | 结论 |
|---|---|---|
| 只改祭祀碑牌基础名称 | 所有祭祀碑牌均显示 `祭祀碑牌=1D`，其他底材不改 | 已有基础表结构支持，但不满足“有词条才显示” |
| 改“神話/絕境”词库 | 修改使用这些词的随机名称 | 条件不准确，而且影响范围不限祭祀碑牌 |
| 改共用碑牌效用描述 | 带效用词条的多种碑牌都出现价签 | 不满足只改祭祀碑牌 |
| 祭祀碑牌专用模板和描述文件 | 仅目标底材的效用词条旁显示 `=1D` | 纯资源候选方案，有静态依据，尚未实机验证 |
| 多属性组合描述 | 尝试同时识别祭祀固有属性与效用词条 | 需验证固有/显式属性是否处于同一描述上下文 |
| 复制物品文本后外部显示 | 按底材与词条准确匹配手工价签 | 可避开内存读取；需要外部工具，不改游戏原生标题 |
| OCR 识别提示框后外部显示 | 识别图中底材和效用词条 | 不读取内存；需要外部工具，准确性低于结构化复制文本 |

### 优先验证的纯资源路线

1. 从当前碑牌模板派生一份祭祀专用模板，保留既有组件与行为，仅指定独立的词缀描述资源。
2. 在独立描述资源中保留原始描述，仅给正值怪物效用分支附加 `=1D`。
3. 仅让祭祀碑牌的基础表行引用新模板，其他七类碑牌仍引用原模板。
4. 验证资源安装工具能否新增并索引新的虚拟路径，以及客户端是否实际按修改后的 `InheritsFrom` 加载这份模板。现有 `Replace` API 的最后一个布尔参数是 `saveIndex`，不能把它误认为“允许新增文件”。
5. 实机核对四组：祭祀有目标词条、祭祀无目标词条、其他碑牌有目标词条、其他碑牌无目标词条；再检查普通/高级词缀提示与原有价格补丁兼容性。

预期显示示例，**不是本次已安装或已验证的截图效果**：

```text
神話 絕境
祭祀碑牌
...
增加12%怪物的效用 =1D
```

该路线不需要读取进程内存，不需要修改 EXE 指令；但比修改一个名称字符串复杂，且会修改基础表的模板引用。当前项目的结构签名会纳入该引用，因此后续若集成，需要核对更新、还原和结构校验流程，不能直接假定现有名称补丁无须适配。

如果顶部名称必须动态出现 `=1D`，本次资源分析没有找到可直接配置的“底材 + 词缀 → 标题”规则入口。尚不能将纯资源词条价签路线扩大解释为动态标题改名已经可行，也没有对整个客户端做不可能性证明。

## 只读复现关键资源

以下命令在本项目根目录使用 PowerShell 7 执行，只读取游戏归档；写入目标是系统临时目录，不会安装补丁：

```powershell
$libDir = (Resolve-Path '.\物价补丁\tools\GGPKExtractor').Path
foreach ($libName in @('SystemExtensions.dll', 'LibGGPK3.dll', 'LibBundle3.dll', 'LibBundledGGPK3.dll')) {
    [System.Reflection.Assembly]::LoadFrom((Join-Path $libDir $libName)) | Out-Null
}
[System.Runtime.InteropServices.NativeLibrary]::Load((Join-Path $libDir 'oo2core.dll')) | Out-Null
$analysisDir = Join-Path $env:TEMP 'poe2-ritual-tablet-readonly-recheck'
New-Item -ItemType Directory -Path $analysisDir -Force | Out-Null
$wanted = @(
    'data/balance/traditional chinese/baseitemtypes.datc64',
    'data/balance/mods.datc64',
    'data/balance/traditional chinese/words.datc64',
    'data/balance/stats.datc64',
    'data/balance/endgamemaptablets.datc64',
    'metadata/items/toweraugments/toweraugment.it',
    'data/statdescriptions/tablet_stat_descriptions.csd',
    'data/statdescriptions/map_stat_descriptions.csd',
    'data/statdescriptions/stat_descriptions.csd'
)
$sourceStream = [System.IO.File]::Open(
    'D:\poe2\Content.ggpk', [System.IO.FileMode]::Open,
    [System.IO.FileAccess]::Read, [System.IO.FileShare]::ReadWrite
)
$ggpk = $null
try {
    $ggpk = [LibBundledGGPK3.BundledGGPK]::new($sourceStream, $true, $false)
    $ggpk.Index.ParsePaths() | Out-Null
    foreach ($record in $ggpk.Index.Files.Values) {
        if ($record.Path -in $wanted) {
            $destination = Join-Path $analysisDir ($record.Path.Replace('/', '_'))
            [System.IO.File]::WriteAllBytes($destination, $record.Read($null).ToArray())
            Get-FileHash -LiteralPath $destination -Algorithm SHA256
        }
    }
}
finally {
    if ($ggpk) { $ggpk.Dispose() }
    $sourceStream.Dispose()
}
```

上面的只读打开、索引解析、资源读取和副本写入方法已在本次分析实际使用。游戏更新后行索引、字段布局、文件哈希可能变化，应重新分析当前版本。

表结构辅助来源：[poe-tool-dev/dat-schema 固定提交](https://github.com/poe-tool-dev/dat-schema/tree/784017383e819fc3be095dce8937873e00bcaf64)，使用 `dat-schema/poe2/_Core.gql` 与共享 `_Core.gql`，未把其最新 schema 等同于本地客户端完整结构。
